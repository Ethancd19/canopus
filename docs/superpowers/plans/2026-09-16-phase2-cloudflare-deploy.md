# Phase 2: Cloudflare Deploy Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run the current site (images still on Cloudinary) on Cloudflare Workers at bycanopus.com via the OpenNext adapter, with a written walkthrough the owner follows for secrets, first deploy, DNS cutover, and rollback.

**Architecture:** `@opennextjs/cloudflare` builds the Next.js app into a single Worker plus static assets. Secrets live in Worker secrets and are exposed on `process.env` at runtime. Prisma keeps the Neon adapter, but the client is created per request on Workers because a socket opened in one request cannot be reused by another. No caching bindings yet: every data page is already dynamic (`revalidate = 0`), and the static pages ship as assets.

**Tech Stack:** Next.js 16.3.5 (upgrade from 16.1.7, required by the adapter), `@opennextjs/cloudflare` 1.20.x, `wrangler` 4.133+, Prisma 7.5 + `@prisma/adapter-neon`, NextAuth v5, Vitest.

**Spec:** `docs/superpowers/specs/2026-09-16-admin-storage-cloudflare-design.md` (sections: Architecture, Auth, Cloudflare deployment, Phases 2).

### Task 3: Per-request Prisma client on Workers

**Files:**
- Modify: `src/lib/db.ts`
- Test: `src/lib/db.test.ts`

**Interfaces:**
- Consumes: `getCloudflareContext` from `@opennextjs/cloudflare` (Task 2).
- Produces: `db` keeps the same name and `PrismaClient` type, so `src/app/page.tsx`, `src/app/work/page.tsx`, and the admin routes need no changes and existing test mocks of `@/lib/db` keep working.

Why: Cloudflare Workers reject I/O on a socket that was opened during a different request ("Cannot perform I/O on behalf of a different request"). The Neon adapter opens WebSockets, so one module-level client shared across requests fails intermittently in production. The fix caches one client per request execution context.

- [ ] **Step 3: Rewrite `src/lib/db.ts`**

```ts
import { PrismaClient } from "@prisma/client";
import { PrismaNeon } from "@prisma/adapter-neon";
import { getCloudflareContext } from "@opennextjs/cloudflare";

function createPrismaClient() {
  const adapter = new PrismaNeon({
    connectionString: process.env.DATABASE_URL!,
  });
  return new PrismaClient({ adapter });
}

// Development: one client for the whole process so HMR does not leak
// connections.
const globalForPrisma = globalThis as unknown as { prisma?: PrismaClient };

// Production (Workers): one client per request. A socket opened while
// serving one request cannot be used by another, and the Neon adapter uses
// WebSockets, so a shared client fails with
// "Cannot perform I/O on behalf of a different request".
const perRequest = new WeakMap<object, PrismaClient>();

function getClient(): PrismaClient {
  if (process.env.NODE_ENV !== "production") {
    globalForPrisma.prisma ??= createPrismaClient();
    return globalForPrisma.prisma;
  }
  const { ctx } = getCloudflareContext();
  let client = perRequest.get(ctx);
  if (!client) {
    client = createPrismaClient();
    perRequest.set(ctx, client);
  }
  return client;
}

/**
 * Prisma client that resolves lazily per request. Import and use it exactly
 * like a normal `PrismaClient` (`db.photo.findMany(...)`).
 */
export const db: PrismaClient = new Proxy({} as PrismaClient, {
  get(_target, prop, receiver) {
    const client = getClient();
    const value = Reflect.get(client, prop, receiver);
    return typeof value === "function" ? value.bind(client) : value;
  },
});
```

# Deploying Canopus to Cloudflare Workers

The site runs as one Cloudflare Worker built by `@opennextjs/cloudflare`.
Static pages ship as assets; dynamic pages and API routes run in the Worker.
Images stay on Cloudinary until the storage phase.

You need: the Cloudflare account that holds the `bycanopus.com` zone (Workers
Paid plan), Node 24+, and the values currently in Vercel's environment
variables.

## 1. One-time setup

```bash
npm install
npx wrangler login          # opens a browser; authorizes this machine
npx wrangler whoami         # confirm the right account
```

Create `.env.local` in the project with the one build-time variable (it is
public, not a secret):

```
NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME=<your cloud name>
```

## 2. Secrets

Each command prompts for the value. Paste it and press Enter. Rotated values
from Vercel are fine here; the Worker is a separate deployment.

```bash
npx wrangler secret put DATABASE_URL
npx wrangler secret put AUTH_SECRET          # openssl rand -base64 32
npx wrangler secret put ADMIN_PASSWORD_HASH  # printf '%s' 'pw' | npm run -s hash-password
npx wrangler secret put ANTHROPIC_API_KEY
npx wrangler secret put RESEND_API_KEY
```

`AUTH_URL` and `NEXTJS_ENV` are plain vars in `wrangler.jsonc` and need no
action. Optional: `npx wrangler secret put ANTHROPIC_MODEL` to change the
tagging model (default `claude-opus-5`).

## 3. First deploy (workers.dev only)

```bash
npm run deploy
```

The output ends with a URL like `https://canopus.<account>.workers.dev`.
Check these before touching DNS:

- [ ] `/` loads, intro plays, featured photos render from Cloudinary.
- [ ] `/work` lists photos with filters working.
- [ ] `/behind` and `/contact` render; send a test message and confirm the email arrives.
- [ ] `/admin` redirects to `/admin/login`; wrong password is rejected; right password lands on the library.
- [ ] In the library, edit a caption and save; refresh; the change persists.
- [ ] Run the AI tag button on one photo and see suggestions.
- [ ] `curl -i https://canopus.<account>.workers.dev/api/admin/photos` returns `401 {"ok":false,"error":"unauthorized"}`.
- [ ] Reload `/work` five times quickly. No 500s (this exercises the per-request database client).

Logs: `npx wrangler tail` streams request logs while you click around.

## 4. Login rate limit

Cloudflare dashboard → the `bycanopus.com` zone → Security → WAF → Rate
limiting rules → Create rule:

- Name: `admin login`
- If incoming requests match: URI Path equals `/api/auth/callback/credentials`
- Rate: 5 requests per 10 seconds, counted by IP
- Action: Block for 10 seconds

Save. This applies once the domain is on the Worker (step 5).

## 5. Move the domain

Do this when step 3 is fully green. Downtime is a few seconds.

1. Dashboard → `bycanopus.com` → DNS → Records. Delete the records that point
   at Vercel: the `A` (or `CNAME`) record for `bycanopus.com` and the `CNAME`
   for `www`. Leave MX, TXT, and anything used for email alone.
2. In `wrangler.jsonc`, uncomment the `routes` block:
   ```jsonc
   "routes": [
     { "pattern": "bycanopus.com", "custom_domain": true },
     { "pattern": "www.bycanopus.com", "custom_domain": true }
   ],
   ```
3. Deploy again:
   ```bash
   npm run deploy
   ```
   Cloudflare creates the DNS records and certificates for both hostnames.
4. Open `https://bycanopus.com` and `https://www.bycanopus.com`. Repeat the
   step 3 checklist on the real domain, especially login (cookies are now on
   the real host).
5. Commit the `wrangler.jsonc` change.

## 6. Turn off Vercel

In the Vercel project: Settings → Domains → remove `bycanopus.com` and `www`.
Then Settings → General → Delete project (or leave it paused). Leaving the
project alive costs nothing but keeps a second copy of your secrets around.

## Rollback

If something is wrong after step 5: comment the `routes` block back out and
run `npm run deploy` (removes the custom domains), then re-create the Vercel
DNS records you deleted (Vercel's Domains page shows the exact values).
The Worker keeps serving on workers.dev throughout.

## Day-to-day

- Deploy a change: `npm run deploy`.
- Rotate a secret: `npx wrangler secret put NAME`, then `npm run deploy` is
  not needed; secrets apply immediately.
- Local Worker preview with real bindings: copy `.dev.vars.example` to
  `.dev.vars`, fill it in, then `npm run preview` (serves on `localhost:8787`).
- Regular development stays `npm run dev`.
